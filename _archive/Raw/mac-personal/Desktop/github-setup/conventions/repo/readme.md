## 1 Starting a repo

### 1.1 From the template

[project-template](https://github.com/vishnuvarthan18/project-template) is a GitHub template repository, so a new project starts from **Use this template**, not a fork or a copied folder. A fork carries the template's history and shows as a fork forever; a copied folder drifts the moment the template changes.

Then make it the project's own:

1. **Set the project identity** by replacing the two placeholders:
   - `PROJECT-SLUG` — the repo name, param-case, used as the directory name.
   - `PROJECT NAME` — the display name, used in `README.md` and `scripts/motd`.

   `make identity` does both across every file — see [§4.1](#41-makefile).
2. **Regenerate the motd banner** — see [§4.2](#42-motd).
3. **Set `VERSION` to `0.0.1`.** `semantic-release` owns it from the first release onward.
4. **Choose the `src/` layout** for the project type ([§2.2](#22-src-by-project-type)) and delete the rest.
5. **Check `LICENSE`** is right for this project, and that the holder matches [§3.1](#31-copyright-and-ownership).
6. **Work through the repository checklist** in [github-conventions §6](../git/github-conventions.md#6-repository-settings) — branch protection and merge settings are once-only and easy to skip.
7. **Write the `README.md`** as the project's own.

### 1.2 Writing the README

Each project's `README.md` describes **the project**, not these conventions. Lead with what it does, and keep this shape:

- **Title** — the product or project name.
- **Description** — one line on what it does and who it is for. Optionally a short "What it does" list underneath.
- **Stack** — the main technologies. A `Layer | Tool` table reads well.
- **Architecture** — data model, module structure, deployment shape: whatever this project actually needs. Skip it if there is nothing to say yet.
- **Commands** — the `make` targets to install, run, build and test.
- **Conventions** — a link back: `See [conventions](https://github.com/vishnuvarthan18/conventions).` Add only the rules specific to this project.
- **License** — one line pointing at `LICENSE`, with the correct holder.

**Do not copy the rules themselves into a project README.** Two copies of a rule is how rules drift, and the copy nearer the code is the one people follow — so the canonical one rots.

## 2 Structure

```
project-slug/
├── src/              # Project source, by type (see 2.2)
│   └── readme.md
├── docs/             # Documentation, notes, references, decisions
│   └── readme.md
├── tests/            # Tests and prototypes
│   └── readme.md
├── releases/         # Shippable outputs — builds, exports, artefacts
│   └── readme.md
├── scripts/          # Helper scripts and the motd banner
│   ├── readme.md
│   └── motd
├── .github/
│   ├── workflows/    # ci.yml, release.yml
│   ├── ISSUE_TEMPLATE/
│   └── pull_request_template.md
├── Makefile          # The single entry point
├── CHANGELOG.md      # Generated by semantic-release
├── VERSION           # Single source of truth for the version
├── .env.example      # Every variable the project reads, with safe defaults
├── .gitignore
├── LICENSE
└── README.md
```

### 2.1 The folder set

**Create all five top-level folders when scaffolding**, even the ones this project does not use yet. Each holds a lowercase `readme.md` saying what belongs in it. That file does two jobs at once: it keeps the empty folder tracked by git, and it documents the folder's purpose. Use it instead of a `.gitkeep`, which does only the first.

The point of creating them all is uniformity. Knowing without looking that `docs/` is `docs/` in every repo is worth more than the tidiness of omitting an empty one.

Two folders earn a note:

- **`releases/`** — things a consumer downloads rather than builds: compiled binaries, exported datasets, packaged artefacts. Committed and tagged, not gitignored build cruft. Empty on most web projects, which ship to a host rather than to a downloader.
- **`docs/`** — the durable written material. Not just API docs: decisions and their reasons, references, investigation notes. When a project accumulates experiments or approaches that were tried and dropped, they go in `docs/` with a note on why, rather than being deleted or left rotting in `src/`.

**This conventions repo is the exception** to the layout above. It ships documentation rather than a product, so its root is a folder per convention domain and the scaffold lives in its own repository.

### 2.2 `src/` by project type

Two layouts, because two kinds of project exist here. Add a third the day there is a third — a speculative layout for work nobody is doing is a rule with nothing behind it.

- **[Web and application software](layouts/web.md)** — Next.js, React, APIs, services.
- **[Data, ML and research](layouts/data.md)** — notebooks, pipelines, models, reports.

### 2.3 Third-party code

Code you do not maintain — an upstream library, a vendored SDK — goes in as a **git submodule** under the relevant `src/` path, recorded in `.gitmodules`. Do not edit it in place: the next update silently drops your change, or silently keeps it and diverges.

Where a patch is genuinely needed, keep it as a patch file in `scripts/` applied by a `make` target, so the change is visible and survives an update.

Prefer the package manager over a submodule wherever the dependency is published. A submodule is for code with no registry presence, or code you need pinned to a commit rather than a release.

## 3 Files

### 3.1 Copyright and ownership

The copyright holder is whoever owns the work:

- **The author** for personal and open work — `Copyright (C) 2026, Vishnu`.
- **The client** for client-owned work — `Copyright (C) 2026, <Client Legal Name>`.

Use the same holder consistently across `LICENSE`, every file header, the `Makefile` header and `scripts/motd`. One repo, one holder. Where ownership is genuinely split, the repo should have been two repos.

### 3.2 File headers

Every source file starts with the licence header, in the comment syntax of the language — `//` for JS/TS/C, `#` for Python and shell, with a `#!` shebang line first where applicable:

```
// SPDX-License-Identifier: MIT
// Copyright (C) 2026, Vishnu
// Author: Vishnu <(removed)>
// Description: This file contains <what>
```

Proprietary work uses `LicenseRef-Proprietary` in place of `MIT`, matching whatever `LICENSE` says.

**JSON has no comments**, so use a `_meta` object:

```json
{
  "_meta": {
    "spdx": "MIT",
    "copyright": "Copyright (C) 2026, Vishnu",
    "author": "Vishnu <(removed)>",
    "description": "This file contains <what> in JSON format"
  },
  "data": []
}
```

- Description format: `This file contains <what>`.
- **No version in a file header.** The version lives in `VERSION`, once ([§4.4](#44-versioning)).
- Exactly one empty line between the header and the file content.
- **Generated files are exempt** — lockfiles, build output, migration files written by a tool. Adding a header to a file a tool rewrites means fighting the tool forever.

### 3.3 Naming conventions

- **param-case** — file names, directory names, URLs, CSS classes, CLI flags, HTML attributes. Brand and product names follow the same rule: `oauth-config.json`, not `oAuthConfig.json`.
- **snake_case** — JSON keys, Python variables and functions, database columns.
- **camelCase** — JS/TS variables, properties and functions, because fighting the language's own ecosystem is a losing convention. `PascalCase` for types, classes and React components.
- **SCREAMING_SNAKE_CASE** — environment variables and true constants.
- **README casing** — only the repo-root `README.md` is capitalised. Folder-level files are lowercase `readme.md`, with an uppercase H1 (`# DOCS`). The capitalisation marks which one is the entry point at a glance.

The apparent inconsistency between snake_case in Python and camelCase in JS is deliberate. A convention that makes every file look foreign to its own language gets abandoned; one that matches the language it lives in gets followed.

## 4 Build

### 4.1 Makefile

**Every repo has a `Makefile` at root, and it is the only entry point anyone needs to learn.** The value is not that make is a good build tool — it is that `make dev` works identically in a Next.js repo and a Python pipeline, so moving between projects costs nothing.

Standard targets:

```makefile
make help       # Default. Prints the motd and this list.
make install    # Install dependencies
make setup      # Prepare the local environment (see 4.3)
make dev        # Run locally
make build      # Build / compile
make test       # Run tests
make lint       # Lint and format check
make clean      # Remove build artefacts
make identity   # Replace template placeholders (scaffold only, then delete)
```

`help` is the default target and prints `scripts/motd` followed by the target list, via `MOTD := ./scripts/motd` and `@cat $(MOTD)`. All targets are `.PHONY`.

Extend per project — `migrate`, `seed`, `train`, `notebook` — but keep the shared names doing the shared thing. **Drop the targets a repo has no use for** rather than leaving one that prints nothing; a target that succeeds silently while doing nothing is worse than a missing one.

**There is no `make release`.** Releases run in CI ([github-conventions §5](../git/github-conventions.md#5-releases)), and a target that appears to cut one from a laptop invites exactly the silent no-op that rule exists to prevent.

**Forward environment variables from a list, not a block each.** A per-variable `ifneq` block invites omission, and the variable nobody remembers to add is the one that breaks a deploy quietly:

```makefile
_FORWARD := API_TOKEN DATABASE_URL SENTRY_DSN
_ENV := $(foreach v,$(_FORWARD),$(if $($(v)),--env $(v)=$($(v)),))
```

### 4.2 motd

`scripts/motd` is a plain text file: an **ANSI Shadow** figlet banner of the project name, then the standard file header in `#` comments.

```
# SPDX-License-Identifier: MIT
# Copyright (C) 2026, Vishnu
# Author: Vishnu <(removed)>
# Description: PROJECT NAME
```

The `Description` here is the project name alone — no `This file contains` prefix. Generate the banner with:

```sh
figlet -f "ANSI Shadow" "PROJECT NAME"
```

`make motd` in the scaffold does this and rewrites the file in place.

It is decoration, and that is the point: `make help` printing the project's name in a banner is how you notice you are in the wrong terminal before you run the wrong command.

### 4.3 Environment

**`.env.example` lists every variable the project reads**, with a safe default or an empty value and a comment saying what it is. It is committed. `.env` is not, ever.

**`make setup` tops up an existing `.env` rather than refusing to touch it.** It appends the keys `.env.example` has and the local file lacks, and never edits a value already set. Refusing when the file exists means a checkout made before a setting existed never learns of it, and that setting then falls back silently at runtime — which is the failure mode nobody debugs, because nothing errors.

### 4.4 Versioning

**A single `VERSION` file at the repo root holds the current version, and it is the only place the version appears.** Not in file headers, not in the `Makefile`, not in `scripts/motd`, not hardcoded in the app. Anything that needs it reads that file.

`semantic-release` bumps it and generates `CHANGELOG.md` from the first release onward, reading the commit format defined in [git-conventions](../git/git-conventions.md). Where a language ecosystem demands its own version field — `package.json`, `pyproject.toml` — the release tool writes it from `VERSION`; it is never edited by hand.

Start at `0.0.1` and stay below `1.0.0` until something depends on the project.
