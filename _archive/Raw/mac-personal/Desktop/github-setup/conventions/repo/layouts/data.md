# DATA, ML AND RESEARCH

The `src/` layout for pipelines, models and analysis. Referenced from [repo §2.2](../readme.md#22-src-by-project-type).

```
src/
├── data/           # Loading, validation, splits
├── features/       # Feature engineering
├── models/         # Model definitions, training, evaluation
├── pipelines/      # End-to-end runnable jobs
├── viz/            # Plotting and figure generation
└── config/         # Experiment configuration
notebooks/          # Exploration — repo root, not under src/
data/               # The data itself — repo root, mostly gitignored
models/             # Trained artefacts — repo root, mostly gitignored
reports/            # Generated figures and written output
```

The three root-level folders are the difference between this and the [web layout](web.md). Data, notebooks and trained artefacts are inputs and outputs, not source, and mixing them into `src/` makes it impossible to say what is version-controlled.

## The data folder

```
data/
├── raw/            # As received. Read-only. Never written to by code.
├── interim/        # Intermediate transforms. Reproducible, disposable.
└── processed/      # Final inputs to training. Reproducible from raw.
```

**`data/raw/` is immutable.** Nothing in the project writes to it. A cleaning step that edits raw data in place destroys the only copy of what you actually received, and no amount of git history brings it back if it was never committed. Read from `raw/`, write to `interim/`.

**`interim/` and `processed/` are gitignored and reproducible.** If a file there cannot be regenerated by running a pipeline, the pipeline is incomplete — write down the missing step rather than committing the artefact.

**What to commit, by size:**

| Size | Where |
| --- | --- |
| Under 1 MB, and it is genuinely source (a lookup table, a label map) | Commit it directly |
| 1–100 MB, and it is needed to reproduce results | Git LFS |
| Over 100 MB, or it is licensed, private, or personal data | External storage. Commit a `data/raw/readme.md` naming the bucket, the exact object, and how to get access |

The threshold matters less than writing it down. A repo where "should this go in LFS" is decided per file ends up with half the dataset in git history and the other half missing.

## Notebooks

**Notebooks are for exploration, and exploration only.** The moment a cell is something you would run twice, it moves to `src/` and the notebook imports it. A notebook that has become the pipeline is a pipeline with no tests, no CLI and a diff nobody can read.

- **Name them `NN-topic.ipynb`** — `01-data-audit.ipynb`, `02-baseline.ipynb`. The number is the order they were written, which is the order they make sense in.
- **Strip outputs before committing.** Configure `nbstripout` as a git filter in `make setup`. Committed outputs make every notebook diff unreadable and quietly put plotted data into git history.
- **A notebook is not reproducible and does not need to be.** Reproducibility is `src/pipelines/`. Do not spend effort making a notebook re-runnable top to bottom; spend it moving the parts that matter out.

## Experiments

**Every training run is configured by a file, not by editing code.** `src/config/` holds the config schema; the actual run configs live under `config/` at the root or are passed as arguments. A hyperparameter changed by editing a Python file is a result you cannot reproduce.

**Log every run** — parameters, metrics, the git SHA, the data version. Whether that is MLflow, Weights & Biases or a CSV appended to by the training script matters much less than it being automatic. A run logged by hand is a run logged sometimes.

**Trained artefacts go in `models/`**, gitignored, named with the run identifier. What gets committed is the config that produced them and the metrics they scored, so any result in `reports/` can be traced to a run.

**Seed everything and record the seed.** Python, NumPy, the framework, and the data split. Then say in the report whether results are stable across seeds — a single-seed result presented as a finding is a coin flip presented as a finding.

## Reports

`reports/` holds generated output: figures, tables, rendered analysis. It is **generated, not authored** — the script that makes a figure lives in `src/viz/` and `make report` regenerates the folder.

Written analysis — the interpretation, the decisions, the things that were tried and abandoned — goes in `docs/`. The split is the same one as everywhere else: `reports/` is output, `docs/` is what you want to still have in a year.
