# ARM Platform — Environment Variables Reference

> Canonical list of every environment variable the platform consumes — which service reads it, whether it is a secret, and which values must stay in sync across services.
>
> **Source of truth for local/CI platform config:** `deploy/arm-deploy-make/.env.example` (copied to workspace-root `.env` by `make env-init`). Per-service `.env.example` files matter when you run a service **natively** outside Docker Compose; under `make local-dev` / `make arm-run`, Compose injects values from the platform `.env`.
>
> After editing `.env`, always run `make env-check`.
>
> **A second validation path now exists.** Each service repo declares the env-var *names* it needs in its own descriptor (`REQUIRED_ENV_VARS`, names only — never values or defaults, so secrets stay out of service repos). `orchestrator generate-compose` checks every declared name against this same platform `.env` and fails the generation — and therefore `make local-dev` or a production deploy — if one is missing. So a name can now be required by a service without appearing in `REQUIRED_CORE_VARS`/`REQUIRED_OPTIONAL_VARS`; `env-check` and the descriptor check are complementary, not the same list. See [DEPLOY-ORCHESTRATION.md](DEPLOY-ORCHESTRATION.md) §4.

## How to read this document

| Column | Meaning |
|---|---|
| **Secret?** | Yes = never commit, never put in GitHub *Variables* (use Secrets). No = safe in Variables / non-secret config. |
| **Required** | Core = `REQUIRED_CORE_VARS` (hard fail). Optional = `REQUIRED_OPTIONAL_VARS` (warn locally, fail in CI). Soft = used by a service but not in those lists. |
| **Local default** | Typical local-dev value. Empty means you must fill it (or let `env-init` generate it). |

Set an optional var to the literal string `skip` to suppress the local warning (“intentionally skipped”).

## 1. Critical cross-service constraints

These are the constraints that cause opaque runtime failures when violated. `make env-check` catches some of them; not all.

| Constraint | Services | Rule |
|---|---|---|
| `JWT_ACCESS_SECRET` | core-be, calendar-be, admin-be | **Identical.** Calendar and admin verify access tokens issued by core-be. Compose also sets calendar’s `JWT_SECRET` from this value. |
| `JWT_REFRESH_SECRET` | core-be only | Not read by calendar-be or admin-be. No cross-repo match required. |
| `GOOGLE_TOKEN_ENCRYPTION_KEY` | core-be, calendar-be | **Identical** and **exactly 64 hex characters** (32 bytes AES-256). Generate: `openssl rand -hex 32`. |
| `SESSION_INTERNAL_SECRET` | session service, core-be, admin-be, calendar-be | **Identical.** Sent as `X-Session-Secret` / `x-session-secret` on east-west calls. |
| `SESSION_COOKIE_SECRET` | session service (platform `.env`) | Signs/validates the session cookie path. Generate: `openssl rand -hex 32`. |
| `MONGODB_URI` ↔ `MONGO_ROOT_PASSWORD` | Mongo init + calendar-be | Password embedded in the URI **must** match `MONGO_ROOT_PASSWORD`. Drift → opaque Mongo auth errors. |
| `MONGODB_URI` ↔ `MONGO_HOST` | calendar-be + mongodb-exporter | **Same host.** calendar-be takes the whole URI; the exporter takes `MONGO_HOST`. Move one without the other and calendar-be fails at boot, long after the deploy reports success. Checked by `env-check-server`. |
| `REDIS_URL` ↔ `REDIS_PASSWORD` | Redis + consumers | `env-init` derives `REDIS_URL` from the password. Keep them aligned if you edit by hand. |
| `SESSION_PUBLIC_URL` / `VITE_SESSION_URL` | core-be, frontends | Local browser-facing session service is **`http://localhost:5001`** (host port). Container listens on 5000. |
| OAuth callback URLs | Google / Azure consoles ↔ env | Must match registered redirect URIs exactly. |
| `CHOKIDAR_USEPOLLING=true` | All app containers (Compose) | Required for hot reload on macOS. Do not remove. |

### Generate secrets

```bash
# JWT secrets (base64)
openssl rand -base64 32

# Session / session service internal / Authelia secrets (hex)
openssl rand -hex 32

# AES-256 token encryption key — MUST be 64 hex chars
openssl rand -hex 32
```

> **Doc drift:** `docs/guides/github-setup.md` still says `openssl rand -hex 16` for the encryption key. That produces **32** hex chars and will fail `env-check` / Joi. Use `openssl rand -hex 32`.

### 2.1a Datastore location overrides (split estate)

Leave every one of these blank for a single host: each service's descriptor already carries the right per-environment default (`arm-*-dev` locally, `arm-*-prod` on the server), and a blank value resolves to it. They exist so a datastore can move off the application host without editing four application repos.

| Variable | Secret? | Required | Notes |
|---|---|---|---|
| `DB_HOST` / `DB_PORT` | No | **Server** | core-be's Postgres. Blank falls back to `arm-postgres-prod` — a container on the app host, i.e. the wrong database |
| `ARM_CORE_DB_HOST` / `_PORT` | No | **Server** | admin-be's read-only mirror of `arm_core` |
| `ARM_ADMIN_DB_HOST` / `_PORT` | No | **Server** | admin-be's own `arm_admin`; may legitimately differ from the mirror |
| `MONGO_HOST` / `MONGO_PORT` | No | **Server** | Consumed by the app services and the mongodb-exporter. `MONGODB_URI` carries its own copy — move both (§1) |
| `REDIS_HOST` / `REDIS_PORT` | No | No | Session storage, read on nearly every request; the worst of the four to put across a network hop |
| `DB_BIND_IP` | No | DB host only | The **database host's own** private IP, used to publish Postgres/MongoDB in `docker-compose.infra.db.yml`. No default on purpose: compose refuses to start rather than bind `0.0.0.0`. Leave empty on the app host |

The four marked **Server** are in `SERVER_REQUIRED_VARS` and enforced by `make env-check-server`, which is a prerequisite of `ci-deploy-prod`. A value beginning `arm-` is accepted — that is the single-host container name — and `check-db-reachable` skips its TCP probe for such a value, since a container name resolves on the compose network but not in the deploy shell.

Caveats before moving anything: none of the four backends enable TLS on these connections (the connection options carry no ssl/tls settings at all), the `docker exec`-based tooling in `make/infra.mk` and `make/backup.mk` only works against containers on the host it runs on, and Kafka advertises its brokers by container hostname, so an off-host Kafka client cannot resolve what the broker tells it to connect to.

### 2.6 Edge domain and off-host backups

| Variable | Secret? | Required | Notes |
|---|---|---|---|
| `SITE_DOMAIN` | No | Soft | **Server only.** The domain `Caddyfile.prod` serves, and the base for `grafana.$SITE_DOMAIN`. Leave empty for local dev |
| `BACKUP_S3_BUCKET` | No | Soft | Enables `make backup-sync`; **empty means backups stay on local disk** and the sync step skips with a warning rather than failing |
| `BACKUP_S3_ENDPOINT` | No | Soft | S3-compatible endpoint (Hetzner Object Storage by default) |
| `BACKUP_S3_ACCESS_KEY_ID` | **Yes** | Soft | |
| `(secret removed)` | **Yes** | Soft | |
| `BACKUP_S3_REGION` | No | Soft | |

**`SITE_DOMAIN` is a deploy-blocking value that `env-check` does not check.** It's in neither `REQUIRED_CORE_VARS` nor `REQUIRED_OPTIONAL_VARS`, so a server deploy with it unset passes validation and then fails later at the edge: Caddy cannot obtain a Let's Encrypt certificate without a real domain whose DNS already points at the host (ACME HTTP-01 needs port 80 reachable from the internet). Set it — and the `grafana.` record — before the first TLS deploy, not after. See [INFRASTRUCTURE.md](INFRASTRUCTURE.md) §3.

The five `BACKUP_S3_*` values are read by `scripts/backup-sync-s3.sh` on the deploy host, not by any application container. See [`runbooks/db-backup-restore.md`](runbooks/db-backup-restore.md).

## 9. Secret vs non-secret (quick map)

**Always secret (GitHub Secrets / never commit):**  
`POSTGRES_PASSWORD`, `MONGO_ROOT_PASSWORD`, `MONGODB_URI`, `REDIS_PASSWORD`, `REDIS_URL`, `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `SESSION_COOKIE_SECRET`, `SESSION_INTERNAL_SECRET`, `GOOGLE_TOKEN_ENCRYPTION_KEY`, `GOOGLE_CLIENT_SECRET`, `MICROSOFT_CLIENT_SECRET`, `SMTP_PASS`, Authelia secrets, Grafana/monitoring passwords, deploy SSH keys.

**Treat as sensitive in CI even if not a cryptographic secret:**  
`GOOGLE_CLIENT_ID`, `MICROSOFT_CLIENT_ID`, `SMTP_USER`.

**Non-secret config:**  
Ports, hostnames, TTLs, public URLs, remote Entry URLs, `TRUST_PROXY_HEADERS`, OAuth *callback URL* strings (still environment-specific), `GITHUB_BASE_URL`, `ROOT`.

CI mapping (prefixed `DEV_` / `STAGE_` / `PROD_`): see [`docs/guides/github-setup.md`](guides/github-setup.md). That guide is not yet fully aligned with Microsoft OAuth, Authelia, Grafana, or `SESSION_INTERNAL_SECRET` — prefer this file + `.env.example` when they disagree.

| calendar-fe `.env.example` `VITE_SESSION_URL=…:5000` | Use `:5001` (Compose already overrides) |
| calendar-be `.env.example` omits `SESSION_INTERNAL_SECRET`, `REDIS_URL`, `OAUTH_CALLBACK_URL` | Still required in real runs |
| admin-be / session service `.env.example` omit `REDIS_PASSWORD` | Needed against passworded Redis |
| Older CLAUDE claims that `JWT_REFRESH_SECRET` must match calendar | **False** — refresh is core-be only |
| Root CLAUDE “notification = Redis/BullMQ” | Notification service is **Kafka + SMTP** |
| `SITE_DOMAIN` looks optional (not in either required list) | **Deploy-blocking for the server** — Caddy can't get a certificate without it (§2.6) |
