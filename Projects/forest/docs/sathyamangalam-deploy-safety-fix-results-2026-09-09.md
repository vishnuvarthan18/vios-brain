### Correction to earlier report (surfaced by the agent itself, post-deploy)
The Step 2 claim that this fix protects the 3 existing-match species "next time they're harvested" is WRONG. `findOrCreateTaxon` looks up taxa by exact `scientific_name` and never overwrites `is_sensitive` on an existing row. The 3 species that already have taxon rows — `Gyps bengalensis`, `Gyps bengalensis (Gmelin, 1788)`, `Melursus ursinus ursinus` — still show `is_sensitive = 0` in live production right now, and always will, since no future harvest will ever re-create those rows.

The fix only protects: (a) the 6 not-yet-harvested species, and (b) any genuinely new name-shape variant. It does NOT retroactively fix the 3 that already exist.

The 6 occurrence rows currently leaking exact coordinates under those 3 taxa remain unprotected until a manual backfill runs:
```
UPDATE taxon SET is_sensitive=1 WHERE id IN (292,799,1110)
-- plus re-coarsening their existing occurrence rows
```

## Gap: 20 vs 3 species count — RESOLVED

`data/atlas.db` is a separate, git-committed SQLite file (generated by `scripts/sync_d1_to_atlas.py`) — not a mirror of live production D1. Different schema (its own `sensitive` column, not `is_sensitive`), 2,664 taxon rows vs. D1's 1,320.

`sync_d1_to_atlas.py` never writes to `atlas.db`'s `sensitive` column at all. That column comes from an entirely separate, older curation pipeline predating the D1/harvest-engine system, independent of `sources/sensitive-species.json` and the matcher fixed in this run.

The script's `SensitivityOracle` class doesn't trust D1's flag alone — it unions three signals: (1) D1's `is_sensitive`, (2) atlas.db's own pre-existing `sensitive` column ("the longer, curated list"), (3) a binomial-prefix check against the registry. All 9 "missing" species were already present in atlas.db's independent 20-taxon curated list before this fix existed — that list is what was used to *discover* the D1 registry's gap in the first place (per the `92b4783` commit message), not the reverse.

So: 20 = atlas.db's separately-curated, always-correct ground truth. 3 = the subset of that ground truth that happens to already exist as taxon rows in live D1, matched against D1's own (buggy, now partially-fixed) flag. Two genuinely different databases, not two views of one dataset.

**Does atlas.db need this fix?** No — never vulnerable to this bug. The Oracle already treats D1's flag as untrustworthy and cross-checks against its own correct list.

**Residual gap (same as the backfill above, restated by the agent):** the Oracle coarsens on atlas.db's export/sync step but doesn't retroactively fix D1 itself. atlas.db was never at risk; live D1 still is, until the backfill (taxa 292/799/1110) runs. Same open item as above — not a new one.
