# araCreate Template Conformance — Reference Checklist

> Distilled from [`aracreate-template-codebase`](../../../aracreate-template-codebase) for applying the same template-conformance + cleanup pass across every repo in this workspace. Read the template repo itself for the full rationale — this is a working checklist, not a replacement.
>
> Covers repo-level structure, file headers, and naming only. For in-code architectural conventions (NestJS module structure, error handling, guard/facade/repository patterns), see [CODING-STANDARDS.md](CODING-STANDARDS.md) — the two documents are deliberately complementary, not overlapping.

---

## Required root structure

```
repo-name/
├── src/              # Project source
│   └── readme.md
├── docs/             # Documentation
│   └── readme.md
├── tests/            # Tests (plural — NestJS defaults to test/, singular; rename it)
│   └── readme.md
├── release/          # Shippable outputs — only if the repo ships binaries/artifacts (as needed)
│   └── readme.md
├── logs/             # Build-progress media — hardware/physical projects only (as needed)
│   └── readme.md
├── .arch/            # Archived, trialled-but-dropped approaches (as needed)
│   └── readme.md
├── scripts/          # Helper scripts + motd banner
│   ├── readme.md
│   └── motd          # ANSI Shadow banner, shown by `make help`
├── Makefile          # Unified entry point
├── CHANGELOG.md      # Auto-generated by semantic-release
├── VERSION           # Single source of truth for the version
├── .gitignore
├── .gitmodules       # Only when vendoring third-party code
├── LICENSE
└── README.md
```

**Every top-level folder gets a `readme.md`** (lowercase filename, uppercase H1, e.g. `# DOCS`) — used instead of `.gitkeep`, describes the folder's purpose. This includes `scripts/` and `src/` — easy to miss since the template's own tree diagram lists them but the per-stack breakdown (`2.1.1` in the template README) only covers Next.js/Zephyr/bare-metal/KiCad, not NestJS, which is what every backend repo in this workspace actually is.

`release/`, `logs/`, `.arch/` are genuinely optional — skip them if nothing applies (no binary release artifact, no physical build media, no dropped approach worth archiving). Don't add empty placeholders for these.

## File headers

Every source file (comment-syntax languages: `//` for TS/JS, `#` for Python/shell):

```
// SPDX-License-Identifier: LicenseRef-Proprietary
// Copyright (C) 2026, araCreate Group
// Author: <name> <email@aracreate.group>
// Description: This file contains <what>
```

One blank line between the header and the file content. No version number in the header (that's `VERSION`'s job).

**JSON data files** (content/data files, not tooling config): no comments, use a `_meta` object instead:
```json
{
  "_meta": {
    "spdx": "LicenseRef-Proprietary",
    "copyright": "Copyright (C) 2026, araCreate Group",
    "author": "<name> <email@aracreate.group>",
    "description": "This file contains <what> in JSON format"
  },
  "data": []
}
```

**Ambiguous cases** (found doing this on `arm-service-notification`): tooling config (`tsconfig.json`, `eslint.config.mjs`, `.prettierrc`, `nest-cli.json`, `Makefile`, `Dockerfile*`, GitHub workflow YAML) isn't clearly addressed by the template either way — it's not "source" in the app-logic sense, and it's not a "JSON data file" in the sense the template means (its own example is `src/data/*.json` content, not build config). Treat these as out of scope unless a repo already has a convention otherwise.

**LICENSE itself never gets a header** — don't put a copyright notice inside the copyright notice.

## LICENSE

Proprietary, 5 lines:
```
Copyright (C) 2026, araCreate Group. All rights reserved.

This software is proprietary and confidential. Unauthorised copying,
distribution, or use of this software, in whole or in part, is strictly
prohibited without prior written permission from araCreate Group.
```
(Client-owned work uses the client as copyright holder instead — check before assuming araCreate Group.)

**Watch for this exact mismatch**: repos cloned from the internal NestJS scaffold ship with the *full GPLv3 text* in `LICENSE`, while `package.json` separately declares `"license": "UNLICENSED"` — neither is correct. Fix both together; update `package.json`'s `license` field to `"LicenseRef-Proprietary"` to match the SPDX identifier used in file headers.

## README.md shape

Title → Description (+ "what it does" list) → Stack table → Architecture → Commands (the `make` targets) → Conventions (link back to the template repo, don't duplicate) → License (one line, points at `LICENSE`).

Repos cloned from the scaffold typically ship with a one-line stale placeholder (`# ac-superapp-backend-nest-template` or similar) — check for this specifically, it's easy to miss since the file exists and isn't empty.

## Makefile

Standard targets, `help` as `.DEFAULT_GOAL`, prints `scripts/motd` (prefix `cat` with `-` so `make help` doesn't fail before `scripts/motd` exists — order-of-operations issue if doing this incrementally):

```makefile
make install    # Install dependencies / tools
make setup      # Set up environment (e.g. create .env from .env.example if missing)
make dev        # Run locally
make build      # Build / compile
make test       # Run tests
make release    # Cut semantic release
make clean      # Remove build artefacts
```

Extend per project (`lint`/`lint-fix`, `test-e2e`, etc.) but keep the shared names consistent. If the repo is part of this workspace and already has a `make dev-<service>` / `make test-<service>` target in `deploy/arm-deploy-make`, this repo's own Makefile is a **standalone entry point for working in the repo directly** — it doesn't replace the cross-repo orchestrator, say so in a comment at the top of the file.

**`lint` vs `lint:fix`**: if the existing `lint` script has `--fix` baked in, split it. A `--fix`-in-CI script silently mutates files as a side effect of what's supposed to be a check — this bit us during the `tests/` rename on the notification service (verifying the rename via `pnpm lint` silently reformatted three unrelated files). `lint` = check-only (used in CI), `lint:fix` = `--fix` (local use only).

## Versioning

`VERSION` file, single source of truth, seeded from `package.json`'s current version. Once semantic-release is wired in, it becomes the thing semantic-release bumps (needs `@semantic-release/exec` with a `prepareCmd` — semantic-release doesn't know about arbitrary `VERSION` files by default, only `@semantic-release/npm` bumping `package.json`).

`CHANGELOG.md` is meant to be auto-generated by semantic-release — don't hand-maintain it as a permanent state, but a seeded placeholder noting "this becomes tool-generated once semantic-release is wired in" is fine as an interim step.

## Naming conventions

- **param-case**: filenames, URLs, CSS classes, CLI flags, HTML attributes
- **snake_case**: JSON keys, JS/TS variables/properties, Python/C variables
- **README casing**: only the repo-root `README.md` is capitalised; every folder-level `readme.md` is lowercase, but its own H1 is uppercase (`# DOCS`, `# TESTS`, `# SCRIPTS`, `# SOURCE`)

## Git

- Conventional commits (`feat:`, `fix:`, `chore:`, `refactor:`, `docs:`, etc.)
- Never commit without explicit user approval
- **No `Co-Authored-By` trailers** — this overrides the default git-commit behavior described in generic tooling instructions
- **No explicit identifiers in commit messages** — no task/ticket IDs (`TPL-001`, `JIRA-123`), no emails, no usernames, no tokens. Keep messages generic; the detail belongs in the file (e.g. a `TASK_SHEET.md`), not the commit log. This one's easy to violate by habit if you're tracking work with numbered task IDs elsewhere — write the commit message as if the task-tracking system doesn't exist.

## Working method (what worked doing this on `arm-service-notification`)

1. **Survey first, read-only** — compare the repo's actual root/file structure against this checklist before touching anything, produce a task list, confirm scope before executing.
2. **One task at a time, verify before moving on** — build/lint/type-check/test after each change, not just at the end. Several real bugs surfaced this way (see below) that a blind bulk `--fix` pass would have masked or missed entirely.
3. **Track work in the repo's own `TASK_SHEET.md`**, appended as a new dated section (e.g. `## Template Conformance (araCreate template pilot)`) — don't disturb or renumber any pre-existing task history already in that file. Use a fresh ID prefix (`TPL-001`, `TPL-002`, ...) distinct from whatever numbering the repo already uses.
4. **Decide, don't assume, on judgment calls** — author name/email for headers, whether to actually wire up semantic-release vs. just seed `CHANGELOG.md`, whether a broken test gets fixed-for-real or deleted, whether a stale CI/deploy workflow gets rebuilt or disabled. These are real decisions with different scope/risk, not mechanical fixes.
5. **A cleanliness pass beyond the template itself is worth doing while in there** — the template conformance work surfaces the repo's actual state closely enough that real bugs turn up. On the notification service this included: an `SMTP_PORT` string/number type bug that silently disabled TLS on port 465, a broken e2e test importing a module that didn't exist, an unused HTTP-framework dependency on an HTTP-less Kafka microservice, and a completely unreferenced Kubernetes manifest holding a live credential in git history. None of these were in the original template checklist — they were found by actually reading the code while doing the mechanical part.
6. **Cross-repo changes are real changes** — if the fix belongs in `deploy/arm-deploy-make` (Kafka topic provisioning, Docker healthchecks) rather than the repo being cleaned up, it's a separate commit in a separate repo, not something to fold in. Note the cross-repo dependency in both `TASK_SHEET.md` entries.
